Overview
Shogunhound is a well-conceived MCP server that bridges Shodan's host intelligence API to LLM agents. The use case is clear and genuinely useful for security analysts, the architecture is clean, and the code reflects real Go experience. For a tool that connects to an external API and surfaces data to an LLM, the security considerations are handled thoughtfully. This is a solid first version.

Architecture & Code Organization
The project structure is excellent — far better than hashchecker. Having cmd/server/ as the entry point, internal/ packages for each domain (validator, cache, shodan, formatter, handler), and DESIGN.md for architectural context is a mature, idiomatic Go layout. Each package has a single clear responsibility. The internal/ boundary correctly prevents the packages from being imported by external code.
One notable design tension: main.go in cmd/server/ is doing two distinct things — MCP server wiring (registering tools, prompts, starting stdio) and tool definitions (all the mcpTool(), countTool(), etc. functions). At ~300 lines, it's approaching the threshold where it would benefit from extraction. The tool definition functions could live in a tools.go file in the same package, and the prompt definitions could move to a prompts.go file. This is a minor point for now but will matter as more tools are added.
The initComponents() function is clean, though it silently defaults the tier to "free" regardless of what the user might want. There's no way to configure the default tier as an environment variable. A SHODAN_TIER env var would make this more flexible.

Security
The security posture is strong and clearly thought through. The API key is read from the environment only, never logged. IP validation is enforced before every API call, not just documented as a policy. The validator correctly handles IPv4-mapped IPv6 addresses (::ffff:192.168.1.1) by normalizing to IPv4 before checking ranges — this is a subtle but important edge case many validators miss. All the relevant RFC ranges (CGNAT, TEST-NET, reserved) are covered.
A few points worth raising:
The handler.go humanizeError function for QueryHost wraps the default error case with the raw error message: fmt.Sprintf("Shodan API error (%s); check your query and try again", err.Error()). Depending on what the underlying library includes in error messages, this could expose internal details to the LLM (and via the LLM to the user). It's worth considering whether to strip the wrapped error message in production output and log it instead.
The mapAPIError function in client.go explicitly acknowledges its own brittleness: it matches on error message strings because go-shodan doesn't expose HTTP status codes. This is a real maintenance risk — if go-shodan changes its error message wording, the sentinel errors silently stop matching and everything degrades to the default "shodan API error" branch. This should be flagged with a test that will fail if the mapping breaks, or tracked as a known issue in DESIGN.md.
The rate-limit sleep shares the same context as the HTTP call (both under the 4-second timeout). The comment in client.go correctly documents this as a known issue: if the HTTP response arrives close to the deadline, the sleep may return DeadlineExceeded even after a successful fetch. The caller is advised to treat this as uncertain, but the handler in handler.go doesn't actually implement that distinction — it treats DeadlineExceeded from QueryHost uniformly as a timeout error. In practice this is likely rare, but the handler should either handle it gracefully or the sleep should operate on a fresh context so the HTTP and sleep timeouts are independent.

The go-shodan Dependency & Tags Field Workaround
The hostResponse struct wrapper to capture the tags field that go-shodan doesn't expose is pragmatic and clearly commented. However, this approach embeds a manual HTTP request construction via c.client.NewRequest and c.client.Do — effectively bypassing the library's GetHostServices method to get access to the raw response. This means you're partially using the library and partially working around it. The README honestly flags this under "Contributing" (Fix for the Tags field limitation), which is good. Consider filing an upstream issue or PR to go-shodan for the tags field, which would eliminate the workaround entirely.

Cache
The cache implementation is clean and correct. Atomic writes via os.CreateTemp + os.Rename are the right approach. The LRU eviction (oldest-by-query-time) on hitting 100 entries is simple and reasonable. The cacheVersion field is present in serialized output but not validated on load — the comment says "not currently validated" which is honest, but when a breaking schema change does happen, the silent incompatibility could cause confusing behavior. A version check on load that gracefully discards the old cache (rather than potentially misinterpreting it) would be safer.
The cache is loaded into memory at startup and written to disk on every Set and Evict. For a tool that handles one query at a time this is fine, but the write-on-every-set pattern means a busy scan (if batch queries are added later) would hit the disk on every result. Batching writes or using a dirty flag would be worth considering at that point.
One issue: the TestCacheEvictsOldestAfter100Entries test uses time.Sleep(1 * time.Millisecond) between entries to ensure distinct timestamps for ordering. This makes the test ~100ms slower than it needs to be (it's the only test not marked t.Parallel() for this reason). A better approach would be to manually set QueriedAt timestamps by directly writing to c.entries in the test, similar to how the other cache tests do it.

Testing
The test suite is well-structured. The validator tests are comprehensive (23 subtests, parallel, covering all the relevant edge cases including the IPv4-mapped IPv6 case). The client_test.go tests use httptest correctly and cover all the important scenarios — success, 401, 429, 404, timeout, malformed JSON, and the subtle context-cancellation-during-rate-limit-sleep case. That last test is particularly impressive; most projects would miss it.
There are notable testing gaps:
There are no tests for handler.go at all. The handler is responsible for parameter extraction, cache integration, error humanization, and audit logging — all meaningful logic. An httptest-based integration test that exercises the full tool handler end-to-end would substantially increase confidence. The README even lists "Handler integration tests" as an area actively looking for contributions, which is the right self-assessment.
The formatter tests are thin. They verify that output contains expected strings but don't validate the structure carefully. There's no test for FormatSearchResult in any format, no test for the formatTagsWithContext annotation logic (honeypot/tor/scanner labels), and no test for the dateWithAge helper (the staleness labels).
There's no test for handler.go's optionalString, optionalBool, or resolvePath functions, which have their own logic worth verifying.

MCP Tool Design
The tool descriptions are excellent — detailed, with format guidance, behavioral hints for the LLM, and explicit ethics statements. The WithReadOnlyHintAnnotation(true) on all tools is correct and meaningful (MCP clients can use this to present the tool as read-only to users).
The two MCP prompts (investigate_ip and recon) are a genuinely useful addition. The step-by-step investigation workflow in investigate_ip is well-designed — it correctly calls shodan_ip_query first, then shodan_dns_reverse, and provides behavioral guidance for CVEs, honeypot tags, and high-risk services. The honeypot warning ("treat as decoy - not a real target") at both the formatter and prompt levels is a good example of defense-in-depth for LLM output quality.
One design question: the tier and history parameters on shodan_ip_query are exposed to the LLM as tool parameters. An LLM is unlikely to know when to set tier=paid or history=true unless the user explicitly asks — these feel more like configuration options than per-query options. Exposing them at the environment variable / config level (with the LLM being able to request history explicitly) might produce cleaner tool calls in practice.

Documentation
The README is excellent — among the best I've seen for a security tool of this scope. The troubleshooting table, the jq log analysis snippets, the manual testing checklist, and the ethics section are all thoughtful additions. The MCP setup instructions for both Cursor and Claude Code are specific enough to actually follow.
A few things to add or improve: there's no CI/CD configuration (no .github/workflows/ directory). For a tool being developed actively and intended for use by security professionals, automated linting and testing on push would build confidence. The AGENTS.md file is present but not linked directly from the README's contributing section, though it's mentioned in the project structure table.

Dependencies
The dependency set is minimal and appropriate. mcp-go for the MCP protocol, go-shodan for the Shodan API client. Both are reasonable choices. No dependency vulnerability scanning is configured. Given this is a security tool, adding govulncheck to CI (once CI exists) would be fitting.

Minor Issues
In formatter.go, collectBanners truncates banners to 200 characters with a simple byte slice (text[:200]). If the banner contains multi-byte UTF-8 characters, this can produce an invalid string. The same truncateRunes function pattern from hashchecker should be used here.
In cache.go, the expandPath function handles ~/ but will incorrectly handle a path like ~username/ — it only expands bare ~ and ~/ but not ~user/ style paths. This is an edge case but worth a comment noting the limitation.
In handler.go, the log file is opened in New() but never closed. For a long-running server this is fine since the OS will close it on exit, but it means there's no way to rotate the log file without restarting the server. Adding a Close() method to ToolHandler (called from main on shutdown) would be cleaner.
The deploy/shogunhound.service systemd unit is present but not documented in the README's "Usage" section. Since it's listed as "for future HTTP/SSE deployment," it could either be removed until that feature exists or noted clearly as experimental.

Summary
This is a well-built, genuinely useful security tool with a clear purpose, clean architecture, and strong security fundamentals. The main gaps are: no CI/CD pipeline, no handler tests, thin formatter tests, and the mapAPIError string-matching brittleness. The rate-limit sleep / context timeout sharing is a known issue that should be resolved before adding batch query support. Compared to hashchecker, the package structure here is significantly better — the internal/ layout is the right way to build a multi-component Go application. Add CI, fill in the handler tests, and this is in very solid shape.
